# FoodMind PostgreSQL Schema Guide

**Status:** Authoritative hand-off for the V1-V11 migration pack

**Schema:** `public`

**Last verified:** 28 July 2026

**Execution proof:** PostgreSQL 18.4 only

**Migration source:** `src/main/resources/db/migration`

This guide defines how to provision, validate, deploy, and evolve the FoodMind
PostgreSQL schema supplied by migrations V1 through V11. The SQL migrations are
the executable source of truth. This document explains their intended
boundaries; it does not replace the constraints, indexes, functions, triggers,
or views in those files.

The recorded validation used a clean local PostgreSQL 18.4 cluster with UTF-8
encoding and `C` locale. It does not prove compatibility with PostgreSQL 15,
16, 17, or any other release. Add and pass an explicit Testcontainers matrix
before claiming support for another PostgreSQL version or locale.

## 1. Operating contract

The migration pack follows these rules:

- Migrations are applied once, in numeric order, by Flyway or an equivalent
  controlled validation runner.
- UUIDs are generated by the application. The schema intentionally does not
  install `uuid-ossp` or `pgcrypto` for ID generation.
- All domain timestamps are `timestamptz`. Runtime JDBC sessions should use UTC.
  User-local analytics explicitly apply `app_user.time_zone`.
- Mutable rows generally carry `updated_at` and an application-managed
  optimistic-lock `version`. The database maintains `updated_at`; it does not
  increment `version`.
- Money is stored as `numeric(10,2)` paired with an uppercase three-character
  currency code. Lower-bound-only numeric constraints explicitly reject
  PostgreSQL `NaN`; finite upper-bound checks reject every numeric special
  value. No view converts or combines currencies.
- Domain enums use uppercase `varchar` values plus checks, not PostgreSQL enum
  types.
- User content with downstream references is retained or soft-deleted.
  Foreign keys are deliberately restrictive.
- JSONB is limited to bounded snapshots, evidence, safe cached responses, and
  safe audit metadata. Core relationships remain relational.
- Search and analytics functions/views are `SECURITY INVOKER`. Database access
  does not replace application authentication or owner predicates.
- Hibernate schema generation must be validation-only outside isolated tests.
  Flyway is the only schema writer.

## 2. PostgreSQL prerequisites

### 2.1 Server and database

The proven setup is:

| Setting | Proven value |
| --- | --- |
| PostgreSQL server | 18.4 |
| Database encoding | UTF-8 |
| Validation locale | `C` |
| Application schema | `public` |
| Required extension | `pg_trgm` |
| Observed `pg_trgm` version | 1.6 |
| ID generation | Application-generated UUID |

Production should also:

- configure database/session timezone as UTC;
- keep one documented database collation/locale for the lifetime of the
  database;
- validate case-insensitive uniqueness and trigram search on that exact
  production locale;
- provide enough storage for tables, indexes, WAL, backups, and migration
  headroom; and
- enable encrypted automated backups and point-in-time recovery before the
  first stateful release.

The migration connection must use a safe search path because V2-V4 contain
unqualified object names:

```sql
SET search_path TO public, pg_temp;
```

No attacker-controlled schema may precede `public` in that path. Revoke public
schema creation before running migrations:

```sql
REVOKE CREATE ON SCHEMA public FROM PUBLIC;
```

### 2.2 Required migration privileges

Use a dedicated migration login that is not the application runtime login. It
must be able to:

- connect to the target database;
- use and create objects in `public`;
- create tables, indexes, views, functions, and triggers;
- alter objects created by earlier migrations;
- create `pg_trgm`, or run after a DBA has installed it in `public`; and
- create and update Flyway's schema-history table.

A production DBA can preinstall the extension:

```sql
CREATE EXTENSION IF NOT EXISTS pg_trgm WITH SCHEMA public;
```

Whether a non-superuser may install the extension depends on the server's
extension policy and privileges. Prefer DBA preinstallation in managed
production. V1 retains `IF NOT EXISTS`, so it remains valid after that
preinstallation.

An illustrative role boundary is:

```sql
-- Run as the database owner/administrator; use environment-specific role names.
CREATE ROLE foodmind_migrator LOGIN;
CREATE ROLE foodmind_app LOGIN;
CREATE ROLE foodmind_backend_exporter LOGIN;

GRANT CONNECT ON DATABASE foodmind TO
    foodmind_migrator,
    foodmind_app,
    foodmind_backend_exporter;

GRANT USAGE, CREATE ON SCHEMA public TO foodmind_migrator;
GRANT USAGE ON SCHEMA public TO
    foodmind_app,
    foodmind_backend_exporter;

REVOKE CREATE ON SCHEMA public FROM PUBLIC;
REVOKE CREATE ON SCHEMA public FROM
    foodmind_app,
    foodmind_backend_exporter;
```

Do not place passwords in migration URLs, shell history, source files, or CI
logs. Use a secret manager, protected environment injection, or a PostgreSQL
password file with restricted filesystem permissions.

## 4. Invariants and responsibility boundary

Database constraints are a final safety layer. They do not authenticate an HTTP
caller, validate an Agent response, perform an object-storage operation, or
replace application use cases.

| Area | Enforced by PostgreSQL | Required from the application |
| --- | --- | --- |
| IDs and concurrency | UUID primary/foreign keys; `version >= 0`; update timestamps | Generate opaque UUIDs; increment/check optimistic-lock versions; map stale updates to a stable conflict |
| Identity | Normalised email uniqueness; account role/status/deactivation shape | Validate email syntax; create adaptive password hashes; never log secrets; authorise account status |
| Timezone | Nonblank stored value; analytics resolver uses valid PostgreSQL/IANA name or explicit UTC fallback | Validate IANA timezone at profile write time; disclose the aggregation timezone returned by analytics |
| Refresh sessions | SHA-256-shaped unique token hashes; same-owner/family successor; immutable token identity; one-way guarded rotation/revocation | Generate high-entropy opaque tokens; rotate atomically; detect reuse; revoke the token family; delete only expired/revoked rows; validate client transport |
| Preferences | Money pairs and numeric ranges; unique taxonomy joins | Interpret hard dietary/allergy rules; validate supported goal/meal-type codes; apply hard filters before ranking |
| Catalogue | Curated status, price, coordinates, classifications, ordered recipes, evidence score shape | Review source data; retire rather than delete; never present observations as inspections/certifications |
| Groups | Membership lifecycle values; at most one active owner; record/member composite references | Ensure every active group has exactly one active owner; check current active membership on every protected command/query |
| Records | Owner FKs, rating/money ranges, soft-delete timestamps, private/group shape, owner-matched media | Derive owner from authentication; enforce active membership before group writes; paginate; never rely on caller-supplied owner |
| Media | Object-key uniqueness; immutable declared/verified metadata; guarded `PENDING -> READY/DELETED` and `READY -> DELETED` transitions | Issue server-controlled keys; verify the object before finalisation; attach only owned `READY` non-deleted assets |
| Want to Try | Exactly one source column and matching source type; active duplicate prevention | Check live source visibility at save and every later resolution; return unavailable after access revocation |
| Search/Explore | Each function owns permission filtering, matching, deterministic keyset order, and `pageSize + 1` limit | Pass the authenticated user ID, bounded query/source allow-list/page, and all-or-none cursor; retain FTS/trigram plan evidence |
| Recommendation sessions | Request immutability, complete status/model/fallback tuple, safe failures, and one-way lifecycle | TX1 ends at `PROCESSING`; do not hold a transaction over Agent I/O; terminalise last in TX2; recover stale rows |
| Recommendation candidates | Unique offering/rank, bounded score/type shape, phase-gated mutation, immutable evidence/reasons | Insert during assembly; insert reasons while eligible/processing; then return candidates before terminalising |
| Feedback | Owner/candidate composite FKs; event-specific payload checks; per-user idempotency; append-only trigger | Prevent contradictory business decisions; treat only explicit accept/reject as labels; no passive negative inference |
| Cooking | Guarded parent lifecycle; inputs append only in `CREATED`; outputs append only in `PROCESSING`; terminal snapshots immutable | TX1 parent/input/processing; remote call; TX2 locked outputs/terminal-last; enforce output cardinality in the use case |
| Chat | Owner session FK; explicit reference origin/nullability; exactly one typed source; same-session message/source FKs | Persist pre-shared references as `USER_SHARED`; re-authorise every source live; validate grounding and retention |
| Idempotency | Unique `(user, operation, key)`; lowercase request-hash shape; response/state/expiry consistency | Canonicalise and hash the request; lock/claim atomically; reject same key with a different hash; cache only safe responses; purge expired rows |
| Audit | Safe metadata must be a JSON object; events are append-only | Allow-list metadata keys/values; exclude tokens, prompts, chat text, comments, and sensitive dietary detail |
| Analytics | Explicit local buckets; Monday week start; null-safe denominators; spending grouped by original currency | Query only the authenticated owner; derive UTC range bounds; define empty responses; never sum currencies without an explicit conversion source |
| ML export | Raw view limits rows to explicit decisions; bounded function selects later signals by decision window and observation cutoff but still returns sensitive raw IDs/features | Run repeatable-read export, domain-separated HMAC user/Meal/offering IDs, exact feature allow-list, null-feature routing, and manifest with decision bounds, cutoff, signal timestamps, schema/commit/count/checksum |
| Deletion/retention | Restrictive FKs and selected soft-delete fields preserve evidence | Implement account anonymisation, session revocation, retention windows, and legal/privacy deletion policy |

Two constraints deserve special attention:

- `group_membership` guarantees **at most** one active owner through a partial
  unique index. Only the create/transfer transaction can guarantee **exactly**
  one.
- Group record foreign keys guarantee that a membership row exists. They cannot
  require its current status to be `ACTIVE`; commands and visibility queries
  must check that live status.

Likewise, the parameterised `foodmind_search_documents_for_user(...)` and
`foodmind_explore_documents_for_user(...)` functions are permission-scoped only
for the user ID passed to them. The Backend derives that argument from its
authenticated/delegated principal and binds the normalized query/source
allow-list/page/cursor values; it never accepts an actor ID from the request.

## 5. Deterministic V11 seed

### 5.1 Provenance and intended use

V11 contains controlled, synthetic MVP data authored for FoodMind fixtures. It
does not ingest production-like free-form internet content and does not create
users, groups, records, sessions, feedback, chat, or cooking history.

Seed properties:

- fixed application-style UUID literals;
- fixed `2026-07-28T00:00:00Z` catalogue timestamps;
- synthetic place names and addresses;
- four synthetic `CLEANLINESS` observations with `source_kind =
  'CURATED_DEMO'`;
- notes explicitly stating that observations are not inspections or safety
  certifications;
- conservative dietary/allergen joins used to exercise hard filtering; and
- `ON CONFLICT (<stable key>) DO NOTHING` on every insert block, so an
  unrelated unique-constraint collision is not silently treated as an exact
  replay.

`ON CONFLICT DO NOTHING` makes an **exact replay of this seed on the same
database** non-mutating. It is not a general catalogue reconciliation
mechanism. Do not replay it into an arbitrary database containing conflicting
natural keys with different UUIDs.

## 6. Validation procedures

### 6.1 Clean PostgreSQL 18.4 validation with PowerShell

The following creates an isolated trust-authenticated loopback cluster. Use it
only on a developer/CI machine. Never enable trust authentication for a
production database.

```powershell
$pgBin = 'C:\Program Files\PostgreSQL\18\bin'
$validationPort = 55447
$validationRoot = Join-Path $env:TEMP 'foodmind-pg18-validation'
$validationData = Join-Path $validationRoot 'data'
$migrationDir = (Resolve-Path 'src\main\resources\db\migration').Path

if (Test-Path -LiteralPath $validationRoot) {
    throw "Choose a new empty validation path: $validationRoot"
}

if (Get-NetTCPConnection -LocalPort $validationPort -ErrorAction SilentlyContinue) {
    throw "Port $validationPort is already in use"
}

New-Item -ItemType Directory -Path $validationRoot | Out-Null
$serverStarted = $false

try {
    & (Join-Path $pgBin 'initdb.exe') `
        -D $validationData `
        --encoding=UTF8 `
        --locale=C `
        --auth-local=trust `
        --auth-host=trust `
        --username=postgres
    if ($LASTEXITCODE -ne 0) { throw 'initdb failed' }

    & (Join-Path $pgBin 'pg_ctl.exe') `
        -D $validationData `
        -o "-p $validationPort -h 127.0.0.1" `
        -w start
    if ($LASTEXITCODE -ne 0) { throw 'PostgreSQL start failed' }
    $serverStarted = $true

    & (Join-Path $pgBin 'createdb.exe') `
        -h 127.0.0.1 `
        -p $validationPort `
        -U postgres `
        foodmind_validation
    if ($LASTEXITCODE -ne 0) { throw 'createdb failed' }

    $migrations = Get-ChildItem -LiteralPath $migrationDir -Filter 'V*__*.sql' |
        Sort-Object {
            [int]([regex]::Match($_.Name, '^V(\d+)__').Groups[1].Value)
        }

    foreach ($migration in $migrations) {
        Write-Host "Applying $($migration.Name)"
        & (Join-Path $pgBin 'psql.exe') `
            -X `
            -q `
            -1 `
            -h 127.0.0.1 `
            -p $validationPort `
            -U postgres `
            -d foodmind_validation `
            -v ON_ERROR_STOP=1 `
            -c 'SET search_path TO public, pg_temp' `
            -f $migration.FullName
        if ($LASTEXITCODE -ne 0) {
            throw "Migration failed: $($migration.Name)"
        }
    }
}
finally {
    if ($serverStarted) {
        & (Join-Path $pgBin 'pg_ctl.exe') `
            -D $validationData `
            -m fast `
            -w stop
    }
}
```

Keep cleanup separate from validation. Confirm the server is stopped and the
resolved path is the intended disposable directory before removing it.

### 6.3 Upgrade validation

An empty-database test is necessary but not sufficient. For every release:

1. Restore a disposable copy of the oldest supported production schema/data.
2. Run `flyway validate` before migration.
3. Record the existing schema-history rows and object/seed counts.
4. Apply only the pending migrations.
5. Run `flyway validate` again.
6. Start Hibernate with `ddl-auto=validate`.
7. Run permission, workflow, analytics, and application contract fixtures.
8. Retain the source commit, database version, before/after Flyway versions,
   duration, and result.

For this initial pack, the minimum incremental test is:

1. apply V1-V10;
2. insert representative users, records, recommendations, feedback, cooking,
   and chat data;
3. apply V11;
4. verify all prior rows and constraints remain valid; and
5. verify deterministic seed counts and candidate queries.

When V12 exists, CI must test both empty-to-V12 and an actual V11-to-V12
upgrade. Never treat an empty migration alone as upgrade proof.

For a PowerShell/`psql` V10-to-V11 rehearsal in the disposable cluster from
section 6.1, use the same numeric parser but stop at version 10:

```powershell
function Get-MigrationVersion([System.IO.FileInfo] $file) {
    return [int]([regex]::Match($file.Name, '^V(\d+)__').Groups[1].Value)
}

$allMigrations = Get-ChildItem -LiteralPath $migrationDir -Filter 'V*__*.sql' |
    Sort-Object { Get-MigrationVersion $_ }

$throughV10 = $allMigrations |
    Where-Object { (Get-MigrationVersion $_) -le 10 }

foreach ($migration in $throughV10) {
    & (Join-Path $pgBin 'psql.exe') `
        -X -q -1 `
        -h 127.0.0.1 `
        -p $validationPort `
        -U postgres `
        -d foodmind_upgrade_validation `
        -v ON_ERROR_STOP=1 `
        -c 'SET search_path TO public, pg_temp' `
        -f $migration.FullName
    if ($LASTEXITCODE -ne 0) {
        throw "Pre-upgrade migration failed: $($migration.Name)"
    }
}

# Insert a committed representative upgrade fixture here, then apply V11.
$v11 = $allMigrations | Where-Object { (Get-MigrationVersion $_) -eq 11 }
& (Join-Path $pgBin 'psql.exe') `
    -X -q -1 `
    -h 127.0.0.1 `
    -p $validationPort `
    -U postgres `
    -d foodmind_upgrade_validation `
    -v ON_ERROR_STOP=1 `
    -c 'SET search_path TO public, pg_temp' `
    -f $v11.FullName
if ($LASTEXITCODE -ne 0) { throw 'V11 upgrade failed' }
```

The fixture must be committed and must exercise foreign keys, owner/group
scope, each workflow state, soft deletion, at least two timezones, and at least
two currencies. Do not substitute an empty V10 database for that fixture.

### 6.4 V11 replay test

Flyway correctly skips an already recorded versioned migration. Replay testing
is therefore a separate disposable-database test:

1. migrate a clean database through V11;
2. capture all V11 table/join counts and an ordered data dump/hash;
3. execute `V11__seed_catalogue.sql` once more with `psql
   -v ON_ERROR_STOP=1`;
4. capture the same counts and ordered dump/hash; and
5. require exact equality.

The proven replay produced zero additional rows and retained:

- 5 cuisines;
- 2 dietary tags;
- 9 allergens;
- 8 meals;
- 4 places;
- 10 offerings;
- 4 observations;
- 3 products;
- 3 recipes;
- 16 ingredients;
- 21 recipe ingredients; and
- 13 recipe steps.

Never manually replay V11 in production. Its idempotency is a fixture-quality
property, not an operational migration strategy.

A PowerShell replay assertion can capture the verification query from section
6.2 before and after direct V11 execution:

```powershell
    (SELECT count(*) FROM place_meal),

}
```

and association table; equal counts alone cannot detect an unintended update.

### 8.2 Immutability policy

Once any shared environment has applied a migration:

- never edit, rename, reorder, delete, or reuse its version;
- never use `flyway repair` merely to suppress an unexplained checksum
  mismatch;
- restore the committed file if a local checkout is wrong;
- investigate schema-history drift before any deployment; and
- retain the schema-history table in backups and migration evidence.

Useful inspection:

```sql
SELECT
    installed_rank,
    version,
    description,
    type,
    script,
    checksum,
    installed_by,
    installed_on,
    execution_time,
    success
FROM flyway_schema_history
ORDER BY installed_rank;
```

### 8.3 V12 and later

All fixes are forward-only:

- use `V12__descriptive_name.sql` for the next change;
- update controlled seed rows by stable UUID/code in V12, not by editing V11;
- add constraints as `NOT VALID` and validate later when a populated-table scan
  would be risky;
- use expand/backfill/contract across separate compatible releases for
  destructive changes;
- batch large backfills and make their progress observable;
- isolate `CREATE INDEX CONCURRENTLY` because PostgreSQL does not allow it in a
  normal transaction;
- add new versioned views instead of silently changing a consumed projection
  contract; and
- add both empty-database and V11-upgrade tests.

Do not create handwritten down migrations as the normal rollback mechanism.
Forward fixes preserve evidence and avoid pretending that destructive data
changes are reversible.

## 9. Production migration runbook

### 9.1 Before deployment

1. Freeze the application and migration commits.
2. Verify every migration hash and run `flyway validate`.
3. Confirm the target reports the expected current version.
4. Confirm only the expected next migrations are pending.
5. Review locks, table scans, index build strategy, disk/WAL headroom, and
   execution time.
6. Verify automated backups and point-in-time recovery are healthy.
7. Take a named pre-migration snapshot for a material production change.
8. Restore the latest backup into a separate database and prove it boots.
9. Run the real upgrade and application contract suite against that restore.
10. Confirm old and new application versions are schema-compatible for the
    deployment window.
11. Record operator, commit, database, PostgreSQL version, start time, and
    approved change ticket.

### 9.2 Applying migrations

- Allow one controlled migrator only.
- Run with the dedicated migration role and safe `search_path`.
- Keep Flyway validation enabled, baseline disabled, out-of-order disabled, and
  clean disabled.
- Stop on the first SQL error.
- Do not run ad hoc DDL beside Flyway.
- Do not expose database credentials or raw migration errors in public API
  responses.
- Start/advance application tasks only after migration success is recorded.
- Verify the current Flyway version, object counts, health/readiness, and
  representative queries immediately after migration.

V1-V11 mainly create new objects and were validated as a clean install. Future
migrations against populated tables require their own lock and duration
evidence.

### 9.3 Least-privilege runtime

After migration:

- revoke all DDL from `foodmind_app`;
- grant only the table DML needed by implemented use cases;
- do not grant the runtime role any privilege on `flyway_schema_history`;
- grant `SELECT, INSERT` but not `UPDATE, DELETE` on `audit_event`,
  `recommendation_feedback`, and `candidate_reason`;
- grant `EXECUTE` on the two search functions and timezone resolver only to
  Backend roles that need them;
- do not grant arbitrary users execute access to functions accepting a user ID;
- grant analytics view access only to the Backend;
- do not grant the Agent, inference service, ML service, Android client, or Web
  client direct PostgreSQL access; and
- keep the Backend-controlled export role separate from the ML consumer.

Because all supplied views and search functions are `SECURITY INVOKER`, a
caller also needs appropriate privileges on their underlying tables. The
regular Backend role already needs bounded table access. Because the restricted
ML source is intentionally raw, its dedicated export role receives `SELECT` on
`ml_interaction_export_source_v1`, `EXECUTE` only on
`foodmind_ml_interaction_export_rows_v1(timestamptz,timestamptz,timestamptz)`,
and only the referenced columns of `recommendation_feedback`,
`recommendation_session`, `recommendation_candidate`, and `place_meal` needed
by these invoker objects—not table-wide grants. It has no access to
user/profile, record/comment, Chat, group
membership, or auth tables. The ML service itself receives only the finished,
validated pseudonymised artifact.

PostgreSQL grants `EXECUTE` on newly created functions to `PUBLIC` by default.
Revoke it explicitly from each sensitive FoodMind function, then grant named
signatures to the Backend role. Do not blanket-revoke extension-owned
`pg_trgm` functions without testing search behavior.

### 9.4 Backup and recovery

- Use encrypted automated backups with point-in-time recovery.
- Take a manual snapshot before a high-risk migration.
- Retain backups according to the approved account/content retention policy.
- Restrict backup restore/decrypt permissions separately from application
  access.
- Test restoration regularly; a successful backup job without a restore test
  is insufficient evidence.
- Restore to a new database/instance, validate schema history and application
  behavior, then switch traffic. Do not overwrite the only damaged database
  during recovery.

### 9.5 Failure and rollback

If a migration fails before commit, keep the application on the old compatible
version, preserve logs, investigate, correct the migration only if it has never
been successfully shared/applied, and rerun in a clean test first.

If a migration has committed:

1. stop further rollout;
2. determine whether the previous application remains schema-compatible;
3. roll back application traffic only when that compatibility is proven;
4. correct schema/data with V12 or later whenever possible; and
5. for unrecoverable destructive damage, restore the pre-migration
   snapshot/PITR into a new target and switch traffic after verification.

Never respond to a production problem with manual `DROP`, an edited historical
migration, `git reset` of database state, or an unreviewed `flyway repair`.
